# Architecture

The tool is a static, client-only browser application. `index.html`, `styles.css`, and `app.js` load `data/manifest.json` with `fetch`, then fetch the selected map/date dataset JSON and minimap asset. The Python preprocessing pipeline reads the source Parquet files and writes the manifest, map/date JSON, and display minimaps. No runtime API, database, CDN, build step, or server-side processing is required. Any deployment must serve these files over HTTP(S) with correct relative paths and JSON/WebP MIME types; opening the HTML directly as `file://` is not supported because browsers restrict `fetch`.

## Data flow and contract

`data/manifest.json` contains `datasets: [{map, date, file, matches:[{id, duration, players}]}]`. Dates are source-folder dates (`YYYY-MM-DD`); a date selects matches represented in that folder. Match IDs remain full, including server-instance suffixes. The manifest's file paths are site-root-relative. Dataset JSON is `{map, date, matches: {[matchId]: {duration, players:[{id, bot, events:[[seconds,u,v,type], ...]}]}}}`. Player events are sorted and retain decoded event names. Seconds are relative to the earliest recorded event across all folders for the match; duration is measured from that baseline. Matches spanning folders are reconstructed globally, with byte-identical duplicate journeys removed, and included in each relevant date's dataset. One supplied match spans two folders; it therefore appears in both date filters but represents one match, not two. The browser consumes normalized coordinates and does not need source-world coordinates.

The pipeline hashes source player IDs consistently into `HUMAN-…` or `BOT-…` IDs, deciding the category from the source ID before hashing. This is stable pseudonymization, not anonymization: IDs can be linked across this dataset, and match IDs are not pseudonymized. Raw source player IDs must not be included in site JSON.

## Map coordinates

Map conversion uses each map's source origin and scale: Ambrose Valley `origin=(-370,-473), scale=900`; Grand Rift `(-290,-290), 581`; Lockdown `(-500,-500), 1000`. For world `(x,z)`, the stored image coordinates are `u=(x-origin_x)/scale`, `v=1-(z-origin_z)/scale`; `y` is elevation and is ignored. The `1-` flips the vertical axis because images have a top-left origin. The browser overlays `u,v` against the displayed minimap width and height. Values outside `[0,1]` are retained, not clamped during conversion.

Worked Ambrose example from the source specification: `x=-301.45,z=-355.55` gives `u=68.55/900≈0.0762`, `v=117.45/900≈0.1305`; overlay fraction is approximately `(7.62%, 86.95%)`. On the source 4320×4320 minimap that is about `(329,3756)` pixels; display scaling changes pixels, not fractions. Source minimap dimensions differ by map (Ambrose 4320×4320, Grand Rift 2160×2158, Lockdown 9000×9000). The pipeline emits aspect-preserving WebP display assets capped at 2048 pixels; do not assume source or display maps are 1024×1024.

## Interpretation and tradeoffs

Timestamp units contradict the supplied README and Parquet type: although `ts` is declared `timestamp[ms]`, its raw integers appear to be Unix **seconds**. For example, raw `1770754537` is 2026-02-10 20:15:37 UTC and adjacent position samples differ by 5, not 0.005, seconds. Treating the raw integers as seconds yields plausible match durations; we subtract the earliest timestamp in each match for playback. This is an evidence-based inference, not a guaranteed schema contract. Dates come from source folders, not inferred from event time. Event bytes are decoded as UTF-8 strings before export.

Combat labels are source event names, not a complete kill feed. The source README describes `BotKill` as a human killing a bot and `BotKilled` as a human killed by a bot, but both labels also occur on numeric-ID bot journeys. Actor/target semantics are therefore unverified: the UI preserves the original labels rather than asserting a victim or killer. Do not infer a particular opponent, successful extraction, or outcome beyond the recorded event. `Position` and `BotPosition` are sampled telemetry, not continuous movement; a path between samples is a visual interpolation. The traffic grid counts recorded samples, so it reflects sample density as well as presence and is intentionally not smoothed. In all-matches playback, the shared cursor denotes seconds since each match's own first recorded event, not synchronized wall-clock time.

The output is compact and easy to host as static files, but client-side filtering and playback operate on downloaded JSON; large datasets therefore cost browser memory and network bandwidth. There are no environment variables or secrets required by the site or pipeline. Because this is production gameplay telemetry, pseudonymized exports and minimaps remain sensitive: restrict hosting to authorized viewers, use private hosting/access controls where appropriate, and do not place the source or generated data on an unrestricted public host without authorization.
